# SkipStream audit (main `ce4a639` plus merged fix packets)

Scope reviewed: the requested content-script ranges, popup, non-cloud-sync options flows, theme/manifests/HTML contracts, and background OpenSubtitles/tab/identity/error paths. Findings below are limited to issues not listed as already known.

## Findings

### H1 — High — CONFIRMED — Firefox options page hangs on callback-style `runtime.sendMessage`

- **Source:** `options.js:412-425`, also `options.js:1192-1193`, `options.js:1409`, `options.js:1520-1538`.
- **Quoted code:** `br.runtime.sendMessage({ type: 'OSUB_STATUS' }, resolve);` and `new Promise(res => br.runtime.sendMessage({ type: 'SUPABASE_GET_ALL', userId }, res))`.
- **What goes wrong:** `br` deliberately selects Firefox's `browser` API when available (`options.js:3`), but these calls pass a Chrome callback as the second argument. Firefox's promise API interprets that position as `options`, rejects/throws, and the wrapper never resolves. Loading options can stop at `await osubEnsureLogin()` (`options.js:489`); Firefox users can be left with loading status and broken login/sync/clear flows.
- **Root cause:** Mixing the callback form with a browser/chrome abstraction that selects the promise-only Firefox namespace.
- **Minimal fix:** Use `await br.runtime.sendMessage(message)` everywhere in `options.js`; remove the Promise wrappers. If callback compatibility is required, branch on the selected API and catch the returned promise.

### H2 — Medium — CONFIRMED — Subtitles are fetched even when the user disables subtitles

- **Source:** `content-scripts/content.js:1400`, `content-scripts/content.js:1651-1677`, `content-scripts/content.js:1805-1809`.
- **Quoted code:** `let _subState = { enabled: true, ... }`; `if (!_subState.subs.length && !_subState.loading) { ... initSubtitles(video, info) ... }`; and `br.runtime.sendMessage({ type: 'OSUB_SEARCH_AND_FETCH', ... })`.
- **What goes wrong:** Setting subtitle-enabled to false only hides rendering; the next identified video still sends its IMDb ID/language to OpenSubtitles and downloads a subtitle. This consumes anonymous/login quota and leaks viewing metadata despite the visible setting being off.
- **Root cause:** The fetch gate checks only whether subtitles are already loaded/loading, not `_subState.enabled`.
- **Minimal fix:** Gate `initSubtitles` at the call site and inside the function with `if (!_subState.enabled) { syncCCBtn(); return; }`; cancel/ignore any in-flight request when the setting changes.

### H3 — Medium — SUSPECTED — A late subtitle response can install subtitles for the wrong SPA episode

- **Source:** `content-scripts/content.js:1651-1677`, `content-scripts/content.js:1800-1809`, `content-scripts/content.js:1845-1857`.
- **Quoted code:** `const result = await br.runtime.sendMessage({ type: 'OSUB_SEARCH_AND_FETCH', ... });` followed by `_subState.subs = parseSubs(result.text);`, with no navigation/video generation check.
- **What goes wrong:** If the user advances or navigates while the OpenSubtitles request is pending, the old response can populate the global subtitle state after the new episode has started. The new video then displays the previous episode's captions (and the later `_resolveSegmentsOnce` call is blocked by the non-empty `subs` array).
- **Root cause:** Subtitle state is global, while the async request is not associated with a video/media ID or `_segGen` generation.
- **Minimal fix:** Capture `video`, media ID, and navigation generation before the request; apply the result only if all still match. Clear/reset fetched subtitle state on media navigation (without changing the already-known global uploaded-file behavior).

### H4 — Medium — CONFIRMED — Portrait/vertical videos are rejected as non-main players

- **Source:** `content-scripts/content.js:1717-1728`.
- **Quoted code:** `if (ar < 1.2 || ar > 3.0) return false;`.
- **What goes wrong:** A prominent 9:16 video (YouTube Shorts, portrait streams, many mobile players) is never attached, so SkipStream does not resume, fetch segments, display subtitles, or install keyboard/skip handling for it.
- **Root cause:** Main-player detection hard-codes a landscape aspect-ratio range rather than distinguishing a large visible player from thumbnails.
- **Minimal fix:** Remove the aspect-ratio rejection or replace it with an area/viewport and z-order heuristic; explicitly allow large portrait videos.

### H5 — Medium — SUSPECTED — A video can miss attachment if metadata fires while it is hidden or zero-sized

- **Source:** `content-scripts/content.js:1731-1740`.
- **Quoted code:** `if (ready === null) { video.addEventListener('loadedmetadata', () => attachVideo(video), { once: true }); return; }`.
- **What goes wrong:** Sites commonly create a video hidden in a preloader/tab and reveal it after metadata has already fired. The one-shot retry then sees `isMainPlayer(video) === null`/false and no later attach is guaranteed if the page makes only CSS/layout changes. The user gets no skipping or resume until a reload.
- **Root cause:** Attachment retries only on one media event; CSS visibility/geometry changes do not fire `loadedmetadata`.
- **Minimal fix:** Keep a bounded retry (or retry on `canplay`/`playing`) until the player is visible, and have `scanVideos` retry unattached videos after layout changes.

### H6 — Medium — SUSPECTED — Native next/skip selectors can click unrelated page controls

- **Source:** `content-scripts/content.js:1085-1104`, `content-scripts/content.js:1106-1130`, `content-scripts/content.js:1211-1219`, `content-scripts/content.js:1244-1251`.
- **Quoted code:** `const el = document.querySelector(sel); ... el.click();` and global selectors such as `'[class*="NextEpisode"]'`, `'[aria-label*="Next Episode" i]'`, and `'[class*="SkipButton"]'`.
- **What goes wrong:** The query is document-wide and does not require that the element belongs to the active player/overlay. On a DOM update or near the end of a video, a visible recommendation, episode-list, or unrelated custom control matching the substring can be clicked, unexpectedly navigating or changing the page.
- **Root cause:** Substring/class and generic-label selectors are treated as authoritative without scoping to the active player or validating the control's nearby video context.
- **Minimal fix:** Scope selectors to a known player root associated with `video`, prefer exact provider selectors, and require a matching accessible label/role before clicking generic selectors; remove broad class-substring fallbacks.

### H7 — Low — CONFIRMED — Iframe pages render a duplicate skip button

- **Source:** `content-scripts/content.js:1298-1327`, `content-scripts/content.js:1356-1361`, `content-scripts/content.js:1380-1387`.
- **Quoted code:** `createSkipBtn(label, onSkip);` executes before `window.top.postMessage(...)`, and the top frame then calls `createSkipBtn(e.data.label, ...)` again.
- **What goes wrong:** A video in an iframe gets one button inside the iframe and another relayed button in the top page. Depending on the iframe geometry, users see two controls or click a control that is visually detached from the player.
- **Root cause:** The child frame creates its local UI even though the same event is intentionally relayed to the top frame.
- **Minimal fix:** In a child frame, relay first and return without local `createSkipBtn` (or choose one rendering owner); only the top frame should render the relayed button.

### H8 — Medium — CONFIRMED — Whole-document mutation observers run in every injected frame

- **Source:** `content-scripts/content.js:1258-1273`, `content-scripts/content.js:1948-1954`, and `manifest.json:39-48`/`manifest-chrome.json:40-49`.
- **Quoted code:** `_skipBtnObserver.observe(document.body, { childList: true, subtree: true });` and `_domObserver.observe(document.documentElement, { childList: true, subtree: true });`, with `"all_frames": true`.
- **What goes wrong:** On ad-heavy/player-heavy pages, every DOM mutation schedules a document-wide video query; a second observer processes every mutation too. Because the manifest injects into all frames on all URLs, pages with many iframes multiply this overhead and may stutter or drain battery even when no usable video exists.
- **Root cause:** Global observers are installed without restricting to a player subtree or stopping when no candidate video is present.
- **Minimal fix:** Observe only a discovered player/container, install native observation after a video exists, disconnect observers when no attached video remains, and use a targeted selector/attribute observer where possible.

### H9 — Medium — CONFIRMED — Resume chooses cloud data from playback position, not recency

- **Source:** `content-scripts/content.js:599-618`.
- **Quoted code:** `const cloudIsNewer = !existingLocal || cloudSaved.p >= (existingLocal.p || 0) - 5;`.
- **What goes wrong:** A cloud record that is only 1–5 seconds behind a newer local offline save is accepted as the source of truth and written back to local storage. Resuming later can put the user behind where they stopped, and the newer local position is lost.
- **Root cause:** The response does not use `updated_at`; a position comparison with a five-second tolerance is used as a recency test.
- **Minimal fix:** Return/compare server `updated_at` and local `t`, or use an explicit monotonic write timestamp/version. Never overwrite a newer local record solely because positions are close.

### H10 — Medium — SUSPECTED — An old async resume request can seek the newly navigated video

- **Source:** `content-scripts/content.js:572-638`, `content-scripts/content.js:1845-1857`.
- **Quoted code:** `const mediaId = getMediaId();` is captured before asynchronous cloud/user-ID work, but `doResume` later executes `video.currentTime = saved.p` without rechecking `getMediaId()`.
- **What goes wrong:** On SPA navigation using the same `<video>`, a slow cloud response for episode A can finish after episode B is loaded and seek episode B to episode A's saved position.
- **Root cause:** `restorePlayback` has no navigation/media generation guard around its awaits and final seek.
- **Minimal fix:** Capture `location.href`/media ID and check them immediately before every seek/toast; invalidate pending restore operations on navigation.

### H11 — Medium — CONFIRMED — Concurrent local cache writes can delete another video's history entry

- **Source:** `content-scripts/content.js:361-378`, `content-scripts/content.js:383-400`.
- **Quoted code:** `const stored = await br.storage.local.get(CACHE_KEY); ... cache[mediaId] = ...; ... await br.storage.local.set({ [CACHE_KEY]: cache });`.
- **What goes wrong:** Two attached videos (or a playback save racing the cloud-to-local bulk sync) can read the same old object, update different keys, and write it back. The later write replaces the earlier one, silently losing one history position.
- **Root cause:** Read-modify-write of the entire cache has no per-tab mutex, version check, or merge-on-write.
- **Minimal fix:** Serialize cache writes in a promise queue, or re-read and merge immediately before setting; use separate storage keys per media ID if practical.

### H12 — Low — SUSPECTED — Out-of-order async saves can queue stale cloud playback

- **Source:** `content-scripts/content.js:414-448`, `content-scripts/content.js:1750-1755`.
- **Quoted code:** `await cacheWrite(...)` occurs before `clearTimeout(saveTimer.id); saveTimer.id = setTimeout(async () => { ... playback_time: Math.floor(pos) ... }, 3000);`.
- **What goes wrong:** `savePlayback` calls overlap. A slower older cache write can reach the timer assignment after a newer call and replace the newer timer, sending an older position to cloud. A later visit may resume behind the user's actual stopping point.
- **Root cause:** Debouncing happens after an await, so it is not a synchronous last-call-wins debounce.
- **Minimal fix:** Clear/set the timer before awaiting storage, or add a monotonically increasing save sequence and have the timer abort unless it is still the latest sequence.

### H13 — Low — SUSPECTED — Native-button observation dies when a SPA replaces `<body>`

- **Source:** `content-scripts/content.js:1258-1273`, `content-scripts/content.js:1972-1976`.
- **Quoted code:** `_skipBtnObserver.observe(document.body, ...)`; navigation reconnects `_domObserver`, but does not reconnect `_skipBtnObserver` unless a same-video URL-change branch happens.
- **What goes wrong:** A site that replaces the body/player shell without changing URL leaves the native skip observer attached to a detached old body. Native Skip Intro buttons added to the new body are then missed.
- **Root cause:** The observer target is not monitored/rebound when the document body changes.
- **Minimal fix:** Observe `document.documentElement` and scope callbacks to current body, or watch for body replacement and disconnect/re-observe the native observer.

### H14 — Medium — SUSPECTED — OpenSubtitles API response controls a host receiving the session bearer token

- **Source:** `background.js:556-572`, `background.js:577-580`, `background.js:614-620`.
- **Quoted code:** `base_url: data.base_url || 'api.opensubtitles.com'`, then ``const base = `https://${sess?.base_url || 'api.opensubtitles.com'}/api/v1`;`` and `headers['Authorization'] = 'Bearer ' + sess.token`.
- **What goes wrong:** No hostname allowlist is applied to `data.base_url`. If the API response is tampered with or a compromised account/API path supplies another host, subsequent subtitle searches/downloads send the user's OpenSubtitles bearer token and API key there.
- **Root cause:** A server-provided URL is persisted and later trusted for authenticated requests.
- **Minimal fix:** Accept only `api.opensubtitles.com`/documented OpenSubtitles hosts after strict URL parsing; discard/normalize `base_url` otherwise. Never send the bearer token to an unapproved origin.

### H15 — Medium — CONFIRMED — Expired OpenSubtitles sessions silently downgrade to anonymous use

- **Source:** `background.js:547-553`, `background.js:577-580`, `background.js:1001-1014`.
- **Quoted code:** `if (sess?.token && sess.expiry > Date.now()) return sess; ... return null;`, followed by search/download using headers with no `Authorization` when `sess` is null.
- **What goes wrong:** After 23 hours, the stored login is never renewed and automatic subtitle fetching continues anonymously. Users lose the logged-in quota and may see subtitles stop after the anonymous daily limit until they manually visit Options and log in again.
- **Root cause:** Passwords are stored by Options, but the background path never uses them to reauthenticate after token expiry.
- **Minimal fix:** On expiry, either re-login once using stored credentials with a clear opt-in/error path, or return an explicit “session expired” status and stop automatic downloads rather than silently downgrading.

### H16 — Medium — CONFIRMED — Opening History sends full Spotify/SoundCloud page URLs to third-party oEmbed services

- **Source:** `options.js:918-934`, `options.js:1061-1073`.
- **Quoted code:** ``https://open.spotify.com/oembed?url=${encodeURIComponent(pageUrl)}`` and ``https://soundcloud.com/oembed?format=json&url=${encodeURIComponent(pageUrl)}``.
- **What goes wrong:** Merely opening the History panel causes saved page URLs (which can contain private playlist/media/account identifiers) to be sent to Spotify or SoundCloud. This is outside the user's configured cloud setting and is not disclosed by the local-history UI.
- **Root cause:** Thumbnail enrichment uses remote oEmbed endpoints with the complete stored URL.
- **Minimal fix:** Make remote thumbnails opt-in, strip query/fragment and user-specific components where possible, or avoid oEmbed and use a local/provider-safe thumbnail strategy. Explain the network request in the UI/privacy notice.

### H17 — Medium — CONFIRMED — Clear Cloud History posts the anon key to an unvalidated configured URL

- **Source:** `options.js:1484-1491`.
- **Quoted code:** `const sbUrl = (creds[S.supabaseUrl] || '').replace(/\/$/, '');` followed by `fetch(`${sbUrl}/rest/v1/rpc/ss_clear_playback`, { headers: { apikey: sbKey, Authorization: 'Bearer ' + sbKey ... }})`.
- **What goes wrong:** Unlike the background's `isValidSupabaseUrl` check (`background.js:213-221`), this destructive options path accepts any stored URL and sends the Supabase anon key there. A mistyped or maliciously configured URL can receive the credential and history-delete request.
- **Root cause:** The direct options fetch bypasses the central URL validation.
- **Minimal fix:** Validate the URL with the same strict HTTPS `*.supabase.co` function before constructing the request, or route the operation through a background message that validates it.

### H18 — Low — CONFIRMED — Import accepts wrong types for almost every active setting

- **Source:** `options.js:1347-1379`.
- **Quoted code:** `safeData[key] = value;` after only object-type checks for three blobs (`skipstream_site_rules`, `skipstream_cache`, `skipstream_stats`).
- **What goes wrong:** A JSON backup containing `skipEnabled: "false"`, `autoNextEpisode: "false"`, a nonnumeric `playbackSpeed`, or malformed subtitle/settings values is accepted. Popup coercion treats nonempty strings as true, so a user can import a file and unexpectedly enable skipping/auto-next or get broken settings.
- **Root cause:** The allowlist controls key names, not value schemas.
- **Minimal fix:** Validate each key's type and range (booleans, known mode enum, finite rate range, subtitle language enum, bounded strings/nested cache entries) before merging; reject or report invalid entries.

### H19 — Low — CONFIRMED — Empty cloud reloads leave stale cloud history displayed

- **Source:** `options.js:1077-1097`, `options.js:1099-1132`.
- **Quoted code:** `let cloudItems = [];` is local, but `_histCloud` is only assigned inside `if (result?.data && result.data.length > 0)`.
- **What goes wrong:** After a sync/reload where the cloud returns an empty list (for example after cloud history was deleted elsewhere), `_histCloud` retains the previous in-memory entries and the merged view still shows deleted history until the Options page is reloaded or the dedicated clear button runs.
- **Root cause:** `_histCloud` is not reset at the start of `loadHistory` or when the cloud response is empty.
- **Minimal fix:** Set `_histCloud = []` before fetching and assign the mapped result even when `data` is an empty array.

### H20 — Low — CONFIRMED — Merged history is not sorted by most recent activity

- **Source:** `options.js:818-841`, `options.js:1158-1159`.
- **Quoted code:** `return [...merged.values()];` with no timestamp sort after local and cloud records are combined.
- **What goes wrong:** The Merged view lists local entries first and cloud-only entries afterward, regardless of `updated_at`/`ts`. Users can see old cloud watches above newer watches and misread what they watched most recently.
- **Root cause:** Deduplication preserves Map insertion order but never sorts the final values.
- **Minimal fix:** Sort `merged.values()` by `_ssTs(b) - _ssTs(a)` before returning.

### H21 — Low — CONFIRMED — Options references a nonexistent subtitle font-size control

- **Source:** `options.js:67-90`, `options.js:480-482`, `options.html:254-287`.
- **Quoted code:** `const subFontSizeInput = $('subFontSize');` and `if ($('subFontSize')) ...`, while the HTML contains only `id="subPosition"` and `id="subPositionValue"` in the subtitle card.
- **What goes wrong:** The supported `subtitle_font_size` setting can be read by content.js but cannot be changed in Options; the code silently does nothing because the element is absent. Users have no visible font-size control despite the setting being implemented.
- **Root cause:** JS and HTML contracts are out of sync.
- **Minimal fix:** Add a bounded `subFontSize` range input/output to `options.html`, or remove the dead JS and clearly make font size unavailable.

### H22 — Medium — SUSPECTED — Subtitle cache has an entry-count cap but no byte/quota cap

- **Source:** `background.js:545`, `background.js:606-612`, `background.js:642-650`, plus the manifests' lack of `unlimitedStorage` (`manifest.json:12-16`, `manifest-chrome.json:12-15`).
- **Quoted code:** `const OSUB_CACHE_MAX = 20;` and `cache[file_id] = text; await br.storage.local.set({ [OSUB_SUB_CACHE]: cache });`.
- **What goes wrong:** Twenty large subtitle files can exceed browser extension storage quota. The write is caught and ignored, after which subtitles/cache/history writes may fail or disappear with no user-visible explanation.
- **Root cause:** Capping by number of files does not cap total UTF-8 bytes, and quota errors are swallowed.
- **Minimal fix:** Enforce a byte budget (evict oldest/ largest entries before writing), measure serialized size, and surface a one-time quota warning; do not let a subtitle cache consume the shared storage budget.

### H23 — Low — CONFIRMED — Strict AMO data-collection declaration conflicts with actual cloud/network telemetry

- **Source:** `manifest.json:51-57`, `content-scripts/content.js:427-439`, `content-scripts/content.js:2035-2061`, and `background.js:1001-1014`.
- **Quoted code:** manifest declares `"required": ["none"]`, while content sends `media_id`, `video_title`, `page_url`, and playback data to `SUPABASE_UPSERT`, and subtitle code sends IMDb IDs to OpenSubtitles.
- **What goes wrong:** This is a release/policy risk rather than an immediate UI error: AMO review or users may reject the package because it declares no required data collection while transmitting browsing/media metadata when configured (and fetching subtitle metadata by default).
- **Root cause:** Manifest declaration and actual data flows are not aligned.
- **Minimal fix:** Reconcile the Firefox data-collection declaration and privacy notice with actual behavior; make optional network features explicit opt-in and document every destination/field.

### H24 — Low — CONFIRMED — Concurrent background errors overwrite each other's diagnostic log entries

- **Source:** `background.js:95-111`.
- **Quoted code:** `const s = await br.storage.local.get(ERROR_LOG_KEY); ... log.push(...) ... await br.storage.local.set({ [ERROR_LOG_KEY]: log });`.
- **What goes wrong:** Two fetch failures occurring together can both read the same old 20-entry log and then write competing versions; one entry batch disappears. Support/error diagnostics underreport failures.
- **Root cause:** The ring buffer is another unserialized read-modify-write operation.
- **Minimal fix:** Serialize `logError` writes through a promise chain, or use a storage primitive/queue that merges with the latest value before each write.

### H25 — Low — SUSPECTED — “Synchronous” unload flush is asynchronous and can lose the last playback save

- **Source:** `content-scripts/content.js:451-478`, `content-scripts/content.js:1773-1776`.
- **Quoted code:** `cacheWrite(mediaId, pos, dur);` is called without awaiting, and the cloud write is started through `getUserId().then(...)` from `pagehide`/`beforeunload`.
- **What goes wrong:** On tab close/navigation, the page can be torn down before either storage write or message promise runs. The last few seconds of playback may not be available locally or in cloud history.
- **Root cause:** WebExtension storage and runtime messaging are asynchronous; `beforeunload` does not keep content-script promises alive.
- **Minimal fix:** Save at a regular interval before unload, use `pagehide` only as a best-effort supplement, and if available route the final payload to a background operation that owns the durable write.

### H26 — Low — SUSPECTED — Subtitle parser rejects commonly encountered non-three-digit millisecond timestamps

- **Source:** `content-scripts/content.js:1415-1428`.
- **Quoted code:** `str.match(/(?:(\d+):)?(\d{1,2}):(\d{2})[.,](\d{3})/)`.
- **What goes wrong:** SRT files encountered in the wild with one or two fractional digits (and similar permissive timestamp variants) produce `NaN`, drop the cue, and show no subtitle text. Whether each variant is accepted by a given SRT/VTT producer needs fixture testing; the UI gives no parse error.
- **Root cause:** The parser requires exactly three fractional digits and silently skips invalid cues.
- **Minimal fix:** Accept `\d{1,3}` and normalize the fraction to milliseconds, or use a tested SRT/VTT parser; report a parse warning when all cues are rejected.

### H27 — Low — CONFIRMED — Re-enabling the master switch loses the user's previous mode

- **Source:** `popup.js:216-229`.
- **Quoted code:** `const nextMode = enabled ? (popupMode === 'off' ? 'auto-all' : popupMode) : 'off';`.
- **What goes wrong:** A user configured Prompt or Auto Intros, turns the master switch off, then turns it on again; `popupMode` is now `off`, so the extension silently changes to Auto All and may skip content the user had intentionally configured not to skip.
- **Root cause:** Disabling overwrites the only in-memory mode with `off`; no last-non-off mode is persisted.
- **Minimal fix:** Persist a `lastActiveSkipMode` (or retain the previous mode before writing `off`) and restore that mode on re-enable.

## Future risks

- Both manifests inject `<all_urls>`/`all_frames` and content.js installs page-wide observers; future browser/site changes can multiply cost and increase the privacy review surface. Restrict matches/frames where product requirements permit.
- MV3 service workers and non-persistent Firefox MV2 event pages can be terminated during delayed `setTimeout` work (notably the five-second settings push in `background.js:494-517`); durable queued/alarm-based work is safer than relying on timers.
- The Firefox manifest's `connect-src` and AMO data-collection declarations should be checked against the current AMO policy and browser CSP validation before release; no build/runtime test was performed here.
